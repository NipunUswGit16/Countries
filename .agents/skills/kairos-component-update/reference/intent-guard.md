# Standing-intent guards — the closed grammar and the orphaned-guard rules

`.kairos/intent.md` is the committed, cross-run intent ledger: one dated bullet per standing fact, each with an optional indented `guard:` asserting the tree state the fact describes. `intent-check.sh` vets the file at Phase 5 start; `promote-intent.sh` is its only writer. This is the single home for three things every consumer of that file needs and used to restate: the closed guard grammar, the whole-file refusal and its one sanctioned repair, and the orphaned-`guard:` ownership/adoption/sweep rules. The phase docs (`phases/5-structural.md` step 1, `phases/8-finalize.md` step 4) and `reference/abort.md` carry the happy path and point here; the clause-by-clause mechanics of the sweep are `scripts/promote-intent.sh`'s header, against `intent-check.sh`'s parser.

## The closed guard grammar

**A guard is never shell, and the grammar is closed.** The **guard trust model** is a security boundary: `.kairos/intent.md` is committed, so its guards are **untrusted input** — cloning a component and running this skill is enough to evaluate every guard it carries, and whoever wrote one need not be whoever runs the migration. `intent-check.sh` therefore never hands guard text to a shell — it tokenizes each guard and invokes the named binary directly, accepting only these forms:

- `test [!] -e|-f|-d|-s <path>`
- `grep -q <pattern> <path>` (add `F` — `-qF`, `-Fq`, `-q -F` — for a fixed-string pattern)
- either form with a leading `!` to invert it

`<path>` is relative to the component root and must stay inside it (no leading `/`, no `..`) and use only `[A-Za-z0-9._/+@-]`, so globs, quoting and whitespace are out of grammar. `<pattern>` is a basic regular expression, printable ASCII only (a control byte or any non-ASCII byte is refused, whether or not `-F` is set), and may not contain shell syntax. Neither `<path>` nor `<pattern>` may start with `-` — that would read as an option, not an argument. The guard token as a whole is capped at 4096 characters, and `guard:` with nothing after it is refused too (an empty guard is not a guard). Multiple `guard:` lines on one entry are allowed and **all must pass**, so an "and" is two guards. A guard that **cannot answer** — unreadable target, timeout — counts as **failed even under `!`**, so `! grep -q X <path>` also needs `<path>` to exist. Anything else — a pipeline, `;`, `|`, `&&`, command substitution, redirects, env-var prefixes, `ls`, `go`, `make`, `-r`/`-i`/`-E`, any other command or flag — is **never executed**: the entry is reported `UNPARSEABLE` and excluded until someone re-confirms it. A richer guard language is a deliberate non-goal; **propose no guard rather than one outside the grammar** — a guardless entry falls back to the resolver-side contradiction rule (`agents/conflict-resolver.md`).

What a guard *can* still do, stated so nobody has to guess: **read**. It can test for, or content-search, any file reachable from the component root — including through an in-tree symlinked directory that points outside it, since the `..`/absolute-path rules are lexical and a symlink is not. What it yields from that read is one pass/fail bit consumed only by the quarantine decision, so it cannot write, cannot execute, cannot report what it read, and cannot see its own result. The other bound is time, and it is per-guard: `GUARD_TIMEOUT` (default 10s) caps one `grep` guard, so a file with N of them caps the sweep at N × that, each reporting its own `QUARANTINED:` line.

## Whole-file refusal and its one sanctioned repair

**Two shapes refuse the WHOLE file, and they are not per-line findings.** A **NUL byte anywhere** in `.kairos/intent.md`, or a **git conflict marker**, makes the entire file one unparseable finding before a line is parsed: `ACTIVE=0`, nothing verbatim copied out, and the reason named on stderr. A conflict marker is matched as a whole line: `<<<<<<<` and `>>>>>>>` require the trailing space their label sits behind, while a bare `=======` tolerates trailing whitespace (and a CR, so a CRLF checkout reads the same) — which is also why a 7-character setext heading underline collides with it; write headings ATX-style (`#`). It fails closed on purpose — past a NUL the line reader cannot see the bytes, and a conflict-marked file holds two versions of every fact interleaved, so no entry means what it says — and `promote-intent.sh` **refuses every action** on such a file too, which is why no row of the re-confirm table can repair it. So do not read `ACTIVE=0` as "this component has no standing intent":

- **Say so explicitly.** Tell the user that `.kairos/intent.md` was refused whole, quote the script's reason line (it names the shape and, for a conflict, the marker's line number), and state the consequence: **every** standing fact is excluded from this run, so no intent steers any resolution until the file is readable.
- **The repair is a hand edit, and it is sanctioned for exactly these two shapes:** resolve the merge conflict (keep the side the user confirms is intended, delete the markers) or remove the NUL bytes, then re-run `intent-check.sh`. This is one of the two places the never-hand-edit rule yields, because the format owner cannot express it — a script that rewrote a file it cannot parse would be guessing at which side of a merge the user wants. Repair the file's readability only: leave every bullet, guard and line otherwise untouched, and make any change to a *fact* through `promote-intent.sh` afterwards, on the re-read file.
- Record it in the migration-log entry the same way the wrong-style-bullet exception below is recorded, and re-run the vet before continuing — a run that proceeds on `ACTIVE=0` from a refused file has silently dropped the component's whole intent ledger.

## Per-line unparseable findings, and how each is repaired

Vetting splits `.kairos/intent.md` three ways: `$RUN/intent-active.md` (guard passed, or no guard), `$RUN/intent-quarantined.md` (guard failed — the fact describes a state the tree no longer shows), and `$RUN/intent-unparseable.md` (lines the parser cannot read). Apply the answers to `.kairos/intent.md` through `scripts/promote-intent.sh`, its format owner — **never by hand** (two narrow exceptions, both where the owner refuses every action and a hand edit is the only way forward: the whole-file repair above, and the wrong-style bullet below), because an edit that leaves a `guard:` at column 0 de-guards the entry above it.

- **re-affirm** — `ACTION=update MATCH="<the fact>" ENTRY="<the same fact>" GUARD="<a guard that attests it again>"` (the date refreshes automatically). Every `GUARD=` must be inside the grammar above, or the next run excludes the entry again; when nothing in the grammar can attest the fact, write it guardless (`DROP_GUARD=1`) and let the resolver-side contradiction rule be the backstop.
- **update** — `ACTION=update MATCH="<the old fact>" ENTRY="<the fact that is now true>"`, plus `GUARD=` to replace the guard or `DROP_GUARD=1` to remove it; omit both to keep the existing one. An entry reported unparseable for an **out-of-grammar guard** is a recognised entry, so it is repaired here: `GUARD="<an in-grammar guard>"` or `DROP_GUARD=1` — the fact is not in question, the guard is.
- **retire** — `ACTION=retire MATCH="<the fact>"`, which deletes the bullet *and* its guard together.

An unparseable **line** is not an entry, so neither `retire` nor `update` can name it: `MATCH` looks up a fact by the exact `- <date>: <fact>` bullet, and a line the parser rejected has no fact to match. Two sub-cases, and only one of them needs your hands.

### Orphaned column-0 `guard:` — the script handles it, entry-scoped by ownership

**The sweep is entry-scoped by ownership, not file-global.** Ownership is judged the way `intent-check.sh` attributes the line, because it is the parser of record: a column-0 `guard:` belongs to the nearest **preceding** column-0 `-` bullet — dated or not — and nothing between them un-owns it (a blank line is *held*, never closing the entry; a `---`, a heading, column-0 prose and a wrong-style bullet do not detach it either), so it is owned by no entry only when no `-` line precedes it anywhere in the file. A `retire` or `update` touches only the orphans owned by the entry it **matched** plus the ownerless ones — with one qualifier that is the parser's own: an orphan it has already reported takes the entry it excluded, so the **second** `guard:` of a run is read against the entry *before* that one, or against no entry at all, and where the two readings could still disagree the verdict is **protect** wherever the rewrite cannot change what the parser reads the line against and a **refusal** (exit 2, nothing written, naming the line and that entry) wherever it can.

- On an **`update`**, when the matched entry is guardless *and* neither `GUARD=` nor `DROP_GUARD=1` was given, **every** orphan that entry **owns** — by the same ownership rule as above, reaching across a blank line or any other structure between the bullet and the orphan — is **adopted**: re-attached as that entry's own indented guards, in file order, the `NOTE:` saying "adopted". Pass either `GUARD=`/`DROP_GUARD=1`, or match an entry that already owns an indented guard, and every orphan that entry owns is **swept** instead, each with its own `NOTE:`. A `retire` never adopts — the entry it would attach to is the one being deleted — so the matched entry's own owned orphans always go, each with a `NOTE:`.
- Every sweep prints its own `NOTE:` carrying the guard's **text**, but only the **column-0** sweep's `NOTE:` also quotes the entry `intent-check.sh` attaches the orphan to — which is not always the bullet directly above. The other spelling's `NOTE:` (below) names that the excluded entry is "whatever entry precedes it" without quoting it, because a closer can detach the guard from any entry in the run; either way the line number and the guard's own text are enough to put the line back.
- The same rules cover the orphan's **other spelling** — an *indented* `guard:` that a heading, a `---` or column-0 prose separated from its bullet, which `intent-check.sh` reports as an orphan too and whose entry it *retracts* — so the matched entry's own are swept or adopted with it in file order and another entry's are left in place; where the parser's attribution of one depends on guard results the script cannot evaluate, the `retire`/`update` is **refused** naming the line, and the way through is to re-indent it directly under the entry it was meant to vet (nothing but blank lines between) and re-run.
- An orphan owned by **any other entry** is always **left in place**, whatever guards that entry already carries: deleting it would flip that entry from `UNPARSEABLE` (excluded, steering nothing) to `ACTIVE` vetted by only the guards that happened to be indented, steering every later resolution with the assertion just deleted. So settling another row of the re-confirm table does **not** clear it, and never tell a reader to wait for someone else's `retire`: its repair is its own row — `ACTION=update` on **that** entry, which adopts every orphan it owns back when that entry is guardless and sweeps them, each with a `NOTE:`, when it is not. Until then it keeps reporting `UNPARSEABLE`.

Never delete an orphaned `guard:` by hand: the script's reading of the shape is the one that stays in step with `intent-check.sh`. The canonical, clause-by-clause statement of the attribution walk — the second-orphan-of-a-run qualifier and the protect-vs-refuse verdict where a rewrite's two readings could disagree — is `scripts/promote-intent.sh`'s header (`orphan_rows()`), read against `intent-check.sh`'s parser.

### A `guard:` hidden behind an unread indent

A `guard:` behind an NBSP or other invisible byte — alone or behind plain spaces (a routine browser/Confluence paste artifact) — is reported and its entry excluded, exactly like an orphan. **`promote-intent.sh` will not adopt or re-state such a line for you.** `update` with neither `GUARD=` nor `DROP_GUARD=1` is **refused** (exit 2, nothing written, naming the line and its assertion): adopting it the way the column-0 orphan repair does — re-emitting the text past `guard:` as a plain indented guard — only looks safe, because the invisible bytes are not confined to the lead, so the adopted guard can still be out of grammar while the run reports "updated" and says nothing. What both scripts actually print as remedies are: state the intent through the owner — `GUARD="<the assertion, retyped in plain ASCII>"`, `DROP_GUARD=1`, or `ACTION=retire` — each of which deletes the stray line with its own `NOTE:`; **or re-indent that line with plain spaces directly under the entry it vets and re-run `intent-check.sh`**, which both scripts' own messages offer and which is sanctioned here, unlike an automated adoption — a fresh parse re-checks the retyped guard against the grammar from scratch, so an invisible byte the parser silently mis-read cannot ride back in unvalidated. What is refused is only `promote-intent.sh` re-stating the line on your behalf without that re-check.

### A wrong-style bullet — the one forced per-line hand edit

A wrong-style bullet line (a `*` or `+` marker, a `-` with no following space, a tab-indented bullet outside an entry) is **the one line-level finding `promote-intent.sh` cannot reach through any action, so a hand edit is the only way forward.** No script action can reach it, and one is deliberately not being added; so `ACTION=append` the well-formed entry, then delete that one stray line by hand in the same edit, and say so in the migration-log entry. The only other **forced** hand edit in this file's life is the whole-file repair above (a merge conflict or a NUL byte, where the format owner refuses every action) — and both are this narrow on purpose: deleting a line the parser never recognised as an entry, or making an unreadable file readable, cannot orphan a guard or de-guard a fact, which is the whole hazard the single-writer rule exists to prevent. (The hidden-guard re-indent above is a hand edit too, but not a forced one: `GUARD=`/`DROP_GUARD=1`/`ACTION=retire` through the owner reach it just as well, and re-indenting is offered as a convenience, not because nothing else works.)
