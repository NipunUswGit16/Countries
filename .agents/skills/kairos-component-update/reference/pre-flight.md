# Pre-flight checks

Implemented in `scripts/pre-flight.sh` — run the script, don't retype it. This doc explains what it checks and why.

It runs before any AI reasoning, branch creation, or merge, and fails loudly on the first failure with an actionable message. Most of its side effects are confined to the component's own `.kairos/migration/` directory (gitignored scratch) — a fresh-mode sweep of stale state, and the template clone into `.kairos/migration/state/template` — plus one idempotent line in `.git/info/exclude`. There is one **tracked**-file side effect: in fresh mode, once every check that can still fail has passed, it removes a committed `.kairos/migration/PLAN.md` left over from a prior run (check 10) — so a tracked deletion in the working tree right after a successful fresh-mode pre-flight is expected, not a sign something went wrong.

## Contract

| | |
|---|---|
| Env in | `PHASE_KEY` (required — stated in `phases/1-preflight.md`; the script refuses to run without it), `MODE` (`fresh` default \| `continue`), `RUN_SOURCE` (`template` default — an unset value means template \| `frontend`; the run's own source, the same name the anchor uses for it, and the switch checks 0b and 3 key off — an unknown value is a hard fail, never a silent fall back to `template`), `TEMPLATE_PATH` (optional local template clone to clone *from*), `TEMPLATE_REPO` (optional URL override, read **only when `TEMPLATE_PATH` is unset** and only as check 7's clone origin — so it is required on a bootstrap without a local template path, where there is no manifest `template.repo` to fall back to, and ignored entirely under `--template-path`; the URL's own hard requirement is Phase 2's bootstrap write, not this script), `FRONTEND_PATH` (optional local checkout of the **frontend** source repo — `--template-path`'s analog for the second upgrade source; check 8.5 normalizes it, check 8.6 clones from it), `FRONTEND_REPO` (optional frontend source URL, read **only** as check 8.6's clone origin and only to *fill a gap* — the manifest's recorded `frontend.repo` wins, so this is the bootstrap case where no block exists yet), `KAIROS_BIN` / `KAIROS_MIN_VERSION` (optional CLI probe overrides), `SWEEP_STALE_RUN` (optional — the escape hatch for check 6's stale-`$RUN` interlock: set it to acknowledge and sweep a `$RUN` that carries an unpromoted `qa-ledger.tsv` but never reached Phase 4, which a fresh run otherwise refuses to destroy) |
| Stdout | `RUN=<path>` and `CACHE=<path>` on success; `TEMPLATE_LOCAL_BRANCH=<branch>` when `TEMPLATE_PATH` is set and its clone is on a branch; `IN_PROGRESS_SOURCE=<template\|frontend>` when a live in-progress block exists; the `FRONTEND_*` lines of check 8.5 when the component has a frontend source at all (a component with no `web/package.json` and no `frontend:` block emits none of them); `FRONTEND_CACHE=<path>` on a frontend run (check 8.6) |
| Stderr | diagnostics, `FAIL:` messages |
| Exit | 0 = proceed; non-zero = stop, relay the message |

Both output paths are fixed: `RUN=.kairos/migration/state` and `CACHE=.kairos/migration/state/template`. The script echoes them so the orchestrator can capture them, but they never vary.

## Checks

**0. Tool dependencies.** `git`, `yq` and `perl` must be on PATH — hard fail otherwise. `yq` must additionally be the **mikefarah** build **at major version 4 or newer**, both probed via `yq --version`. Two separate failures: the python `yq` (kislyuk, a jq wrapper) takes different flags and fails incompatibly — loudly in `yaml-gate.sh`, silently in `collect-common.sh`, which then reports OK having resolved zero common modules; and mikefarah **v3** clears the flavor check (it reports `yq version 3.4.1`, the same spelling early v4 builds use) while every v4-only construct the skill relies on — `strenv()` and the `tag` operator in `in-progress.sh`, `-p=json` in `collect-common.sh` / `codev-check.sh`, `yq e` in `yaml-gate.sh` — fails several phases later. The major version is read from after the last `version` in the output, so both v4 spellings pass (`yq (https://github.com/mikefarah/yq/) version v4.x.y` and the older bare `yq version 4.9.6`). `perl` is load-bearing because `intent-check.sh` runs every *content* guard (`grep -q …`) under a `perl -e 'alarm …'` timeout; without it one missing tool reads as N failing guards (path tests are answered by a shell builtin and need nothing). `go` joins them **when the component root has a `go.mod`**: Phase 3.5 parses it twice with the go tool (the co-dev wrong-target tripwire in `codev-check.sh`, and `collect-common.sh`'s module list) and both hard-fail without it. Probing here is the same philosophy as check 0b — fail before any state is written, rather than mid-phase after Phase 3.5 has already taken a branch. A component with no `go.mod` is unaffected.

**0a. Run from the component root (the git work-tree toplevel).** Refuses anywhere but the component root — `git rev-parse --show-toplevel` compared against `pwd -P` (the physical path, so a symlinked ancestor cannot make the root look like a subdirectory). This is a hard stop, not a normalization, because every check below is anchored at the root and each fails *silently wrong* from a subdirectory rather than refusing: check 1's dirty scan is pathspec-scoped to `.`, so from `web/` it reports clean while the root is dirty; checks 3 and 6 read `.kairos/manifest.yaml` by relative path, so from a subdir it is invisible and **both** live-run refusals skip while a fresh run sweeps a live one; and checks 5/6/9 create `.kairos/migration/state` under the cwd, so a subdir run spawns a second state dir at `web/.kairos/migration/state`. A frontend run legitimately `cd`s into the mount in later phases (4.5/7/8), so being invoked from there is a realistic mistake — one toplevel comparison closes all of it. A path that is not inside a git work tree at all (a bare or mirror clone) is refused with a distinct message.

**0b. Kairos CLI, at a version that can materialize template trees.** Phase 2.5 builds both merge sides of a **template** run by invoking `kairos component create` (see `materialization.md`), so the CLI is a hard dependency of every template migration — there is no substitution-map fallback path. Three checks, all before any state is written (and all skipped on a frontend run — see below):

1. `kairos` on PATH (overridable with `KAIROS_BIN`).

   Then a **warm-up**: one throwaway invocation, output and exit status discarded. Every `kairos` invocation may bootstrap or settle a pending install first (reinstalling dependencies, applying version-state migrations); this is deliberate, letting that work land before the probes below and materialization later depend on a settled install.

   **Best-effort by design.** The CLI has no on-invoke self-updater and no flag to force a pending update to complete, so nothing here can guarantee the install stays still for the rest of the run. The load-bearing defense is `materialize.sh`'s retry-once around `component create`; the warm-up only narrows the window.
2. `kairos --version` ≥ **0.3.12** (overridable with `KAIROS_MIN_VERSION`). The comparison is field-wise numeric, not lexical — `0.3.10` must compare *below* `0.3.12`, which a string compare gets wrong. The version is read from the last version-bearing line of the output, because the CLI may print an auto-update notice first and that notice itself contains version numbers.
3. `kairos component create --help` advertises `--no-tidy` and `--no-frontend`. On a **facade** (`.kairos/manifest.yaml` `template.kind: facade`, else `.init.mk` sets `MASTERDATA_INCLUDE_NO_CDC`, or sets `GENERATE_MODULES` without `sql` or `all`) the probe is `kairos component facade create --help` for `--no-tidy` and `--template-path` instead: a facade is materialized with that subcommand, which exists from CLI 0.3.35 and has no `--no-frontend`. Pre-flight prints `COMPONENT_KIND=facade`; a proper component gets no such line. The kind is not recorded on the anchor: any phase re-derives it from the same two files.

Check 3 is not implied by check 2: a local checkout can report a new version while missing the flags (mid-rebase, or a partially applied update). The flags are what actually matter, so they are probed directly.

The probe checks only `--no-tidy` and `--no-frontend`, not the full defensive set materialize passes (`--no-repository --no-skills --no-tidy --no-frontend` plus `KAIROS_SKIP_NAME_VALIDATION`, catalogued in `reference/materialization.md`). That is a deliberate representative gate, not an oversight: these two are the ones whose *absence* turns materialize into an interactive hang (the frontend picker) or a network/toolchain dependency (tidy), so they are the sharpest version signal — and materialize itself surfaces a hard "unknown flag" error if the CLI rejects any of the others, so a stale CLI that slips past this probe still fails loudly there rather than silently.

**A frontend run needs none of this, and under `RUN_SOURCE=frontend` it pays none of it** — nothing on that arm materializes through `component create`; the merge sides are the module subtree plus the CLI's replacement map applied by the skill itself (`scripts/lib/frontend-substitute.sh`), and the CLI could only clone the frontend at branch HEAD, which is neither BASE nor TARGET. So on a frontend run check 0b reports **not applicable** — one INFO line, no probe, no version floor, no hard stop — and a template run (`RUN_SOURCE` unset or `template`) pays exactly the three checks above, byte for byte. "Not applicable" is deliberately a different claim from "old": the run is not degraded, the dependency simply is not one. The CLI-parity claim the probe would otherwise stand behind is carried instead by the contract test in `tests/materialize-frontend.test.sh`, which pins the skill's replacement map to the CLI's.

Failure is a hard stop naming the version floor and telling the user to update `nga-local-dev`. This is deliberately the earliest possible failure point: discovering a stale CLI mid-materialization means a half-written migration to unwind, whereas failing here leaves nothing to clean up.

**1. Clean working tree.** Only tracked-file modifications count. The check is a `git diff --quiet` / `git diff --cached --quiet` pair — it passes when no tracked file has staged or unstaged changes, and ignores **all** untracked files regardless of where they live (an untracked file in a tracked directory is fine, exactly as one in an untracked directory is), gitignored files included. The point: `--abort` must be safe — anything uncommitted at migration end is presumed to be the AI's in-progress work. Untracked files are a special case abort handles on its own evidence (`reference/abort.md`): it deletes only what the run's own records prove the run wrote, and surfaces the rest to the user rather than sweeping it.

Under `MODE=continue` the pair carries **four** `:(exclude)` pathspecs — `.kairos/migration-log.md`, `.kairos/intent.md`, `.kairos/manifest.yaml` and `.gitignore` — because all four are dirty **by design** mid-run. The first two are the ordinary case: every migration-log entry is written after the commit it describes and rides the *next* commit, and intent promotion appends to `.kairos/intent.md` before Phase 8's finalize commit carries it. `.kairos/manifest.yaml` is the third because two resume windows `reference/continue.md` names verbatim leave it staged or modified: a kill after Phase 4's in-progress `set` but before the scaffolding commit, and a kill inside Phase 8 step 5 between the baseline `advance` and the commit that carries it. `.gitignore` is the fourth because that same mid-Phase-4 window leaves it **staged**: Phase 4 runs `git add .gitignore` (the state-dir ignore migration on the legacy components this skill targets) several statements before the scaffolding commit, so a kill there leaves a staged `.gitignore`; abort's mid-Phase-4 arm unstages it, and continue must not refuse the same window. Without those exemptions the windows would be unreachable — every triage arm runs this pre-flight first, `reference/continue.md` forbids committing or stashing past it, so a refusal on any of the four would send the reader back to the arm that sent them here. Without the exemption at all, every legitimate resume after Phase 5 — including the clean checkpoint Phase 7 explicitly tells the user to resume from — would be refused as "dirty". Dirt beyond those four paths still refuses, with a pointer to `reference/continue.md`'s triage (which owns the interrupted-work shapes and their path-scoped reset).

**2. On a branch** (not detached HEAD).

**3. No live migration in the way** (unless `MODE=continue`). **Either in-progress block counts, and both at once is refused.** A component is assembled from two upgrade sources, so a live run records `template.in_progress` *or* `frontend.in_progress`; the script reads both keys (fail-closed on an unreadable manifest, as before), and a manifest carrying **both** is a hard failure rather than a resolved one — the two blocks answer the same three questions (which branch, which target, which rollback SHA) with different values, and no reader can pick. Every field the refusals below quote then comes from whichever block is live, and the script says which on stdout as `IN_PROGRESS_SOURCE=<template|frontend>` (emitted only when a block exists) so continue and abort act on that source's block instead of inferring it from a branch name. Four more refusals below — but `fail` exits on the spot, so at most **one** of them ever fires per run. In fresh mode (`MODE` unset or `fresh`) the script checks the first three in this order; the fourth exists only in continue mode, where the first three are skipped entirely:

- **1. On a migration-shaped branch with an in-progress block** — the current branch equals the live source's `in_progress.branch` in `.kairos/manifest.yaml` (`template.` or `frontend.`, whichever exists — authoritative, because branch names are user-confirmed), or, when the block exists with no `branch:` (a `--no-branch` migration), equals its `previous_branch`, **or** simply matches either suggested glob — `topic/*/template-update-*` or `topic/*/frontend-update-*` — whatever the block names. That last arm is wider than "the migration branch": any migration-shaped branch takes it, including one left behind by an unrelated older run. Fail: run continue/abort or switch branches first — and note that the message's "switch branches" is a remedy for the *user*, never something the orchestrator does on its own (`phases/1-preflight.md` states the rule). Checked **first**, so on a migration-shaped branch with a live block this is the one that fires — it pre-empts refusal 3 below (which never gets evaluated once this one has exited).
- **2. On a migration-shaped branch with no block** — matches either suggested pattern (`topic/*/template-update-*`, `topic/*/frontend-update-*`) but the manifest records nothing (Phase 4 died between `checkout -b` and the manifest write). There is no run for continue or abort to act on, so the message gives the working remedy: switch off the branch and delete it. **`RUN_SOURCE=frontend` is what tells the chained case apart from that crash window** — they have the same shape and opposite meanings. A frontend run chained after a *finished* template run stands on that run's migration branch with no live block **by design** (Phase 8 cleared `template.in_progress`, the consent step got a yes, and the frontend run keeps the branch so one PR carries both); a frontend-only invocation started while standing on a finished migration branch is the same state. Under `RUN_SOURCE=frontend` that block-less shape is therefore **accepted** — an INFO line saying it was read as the chained/frontend re-entry, and the source recorded on the anchor — instead of refused. Without the env it refuses exactly as before, and the refusal now names the env as the way to declare the other reading. A **live** block of either source is untouched by this: it still takes refusal 1, chained or not, because "one migration at a time" is what chaining sequences, not what it relaxes. Mutually exclusive with refusal 1 by construction — a branch is either block-present or block-absent, never both — so this one is never the one refusal 1 pre-empts.
- **3. Fresh over a live run, from any branch** — the block exists and `MODE` isn't `continue`. Fail naming the live source, its target and its branch, and offering continue or abort. This one is not about where you are standing: the block suppresses check 6's sweep, so a fresh run started elsewhere would silently inherit the live run's `$RUN` (qa-ledger answers, spawns, `context.env`). There is deliberately **no override flag** — abort is the escape hatch. Checked last of the three, which is why refusal 1 pre-empts it: standing on the migration-shaped branch with the block still present means the *branch* refusal already fired, before the script ever reaches this one.
- **4. `MODE=continue` with a contradicting `RUN_SOURCE`** — the one thing check 3 enforces in continue mode, where refusals 1-3 are deliberately skipped (a resume stands on the migration branch over a live block by design). The live block **is** the run's source, so a caller-supplied `RUN_SOURCE` naming the other one cannot also be right: check 9 would record it onto the anchor (last write wins) and the resumed run would take the wrong arm — wrong target chain, wrong upgrade-file directory, wrong gate cwd — until Phase 8's advance cross-check finally noticed. Fail closed, before anything is recorded, naming both values. Only when **both** are known: an unset `RUN_SOURCE` on a resume is the ordinary case (continue derives the source from the block), and a resume with no live block is `reference/continue.md`'s own lost-block triage.

**4. Component metadata present OR bootstrap will run.** Missing `.kairos/manifest.yaml` is NOT a hard failure — Phase 2 handles it via bellwether detection. The script prints an INFO line so the orchestrator knows bootstrap is coming — and that is all this check does: **it enforces nothing about the repo URL.** The orchestrator still determines the URL (origin remote, the user, or the canonical kairos-component-template URL), but `TEMPLATE_REPO` is consumed only by check 7, only as the clone origin, and only when `TEMPLATE_PATH` is unset — so a bootstrap launched with `--template-path` passes here and through check 7 without a URL at all. The hard requirement lands one phase later, at Phase 2's bootstrap manifest write, where `in-progress.sh` refuses an empty `REPO`.

**5. Ignore the state dir before it exists.** Appends `.kairos/migration/state/` to `.git/info/exclude` (idempotent), ahead of check 6 creating the directory and check 7 cloning tens of MB of git objects into it. Without this the state dir — including each bare clone's stock `hooks/*.sample` files — floods `git status` for the whole run.

Deliberately `.git/info/exclude` rather than `.gitignore`: the state dir is local scratch, and editing a tracked file here would dirty the working tree check 1 just demanded be clean, leaving a stray edit to unwind on abort and blocking a re-run after a later check fails. Phase 4 still writes the durable, shared `.gitignore` entry (and migrates a legacy broad `.kairos/migration/` pattern, which would otherwise hide the committed `PLAN.md`) — it tests for the literal pattern rather than calling `git check-ignore`, which this exclude would already satisfy.

**6. Sweep stale state.** One migration runs per repo at a time, so `.kairos/migration/` is a single fixed directory (`state/` scratch + the committed `PLAN.md`). In fresh mode, any leftover `.kairos/migration/` is scratch from a completed or crashed prior run — remove it so we start clean. The exceptions are the **mirror clones**: the template at `state/template`, the `kairos-component-common` mirror at `state/common`, and the frontend source's at `state/frontend`. All three are spared and refreshed in place — the template by check 7, the frontend by check 8.6, the common mirror by `clone-common.sh` (`remote update --prune`, and a clear-then-re-clone if the mirror is partial) — because git objects are immutable and re-fetching is far cheaper than re-cloning. (The incident that pinned the frontend mirror into the spared set is recorded at the sweep in `scripts/pre-flight.sh`.) Never sweep when a migration is in progress (the manifest's `template.in_progress` block is the guard — continue still needs `PLAN.md` and `state/`, however old). In fresh mode check 3's third refusal now stops the run before this point, so the guard here is the second line of defence, not the first.

**The fresh-invocation interlock (before the sweep).** Check 3 and this sweep both key on the in-progress *block*, which Phase 4 does not write until after all the asking is done — so a run still live in **Phases 1–3.5** has an unpromoted `$RUN/qa-ledger.tsv` (its Phase 3.5 answers), a `model.txt`, synthetic trees and a classification, and **no block** for continue or abort to recover them from. Without a guard, a *second* fresh invocation launched into that window sweeps all of it and exits 0; abort's no-block arm then reports "only the ledger" — already deleted. So before sweeping, a fresh run **refuses** when a non-empty `qa-ledger.tsv` sits over a `$RUN` that never reached Phase 4. "Never reached Phase 4" is read as **`PREV_SHA` absent from `context.env`**: Phase 4 anchors `PREV_SHA` on every path (create / skip-create / `--no-branch`) before it writes the block, and Phase 8 re-anchors it — so a *finished* run's leftover (block cleared, `$RUN` kept for post-mortem) carries `PREV_SHA` and sweeps as before, the ordinary "start the next migration" path; only the pre-Phase-4 window has a ledger but no `PREV_SHA`. Two exemptions: `RUN_SOURCE=frontend` (the chained frontend re-entry sweeps the finished template run's `$RUN` by design — `phases/8-finalize.md`), and `SWEEP_STALE_RUN=1`, the escape hatch for a genuinely stale pre-Phase-4 leftover (a crash before Phase 4, or an abort whose no-block arm already salvaged the ledger). The refusal names both continue/abort and `SWEEP_STALE_RUN=1` as remedies.

**7. Template source reachable, cloned into the migration state dir.** The clone is per-component and lives inside the repo at `.kairos/migration/state/template` — no shared home-directory cache, so components never share a clone or race on one.

- **Facade default and kind check** (only without `TEMPLATE_PATH`). On a facade bootstrap with no `TEMPLATE_REPO`, the origin defaults to `git@ssh.bitbucket.org:ifs-pd/kairos-component-facade-template.git`, with an INFO line, and pre-flight prints `TEMPLATE_REPO=<that URL>`; Phase 2's manifest write records the same URL as `REPO`. A proper component has no default here. An origin naming the other kind's template (`kairos-component-template` for a facade, `kairos-component-facade-template` for a component) is refused before the clone; other names pass, and `materialize.sh` checks each template tree's `go.mod` module line either way.
- Resolve the clone origin: `TEMPLATE_PATH` (a local git repo — working tree, linked worktree, submodule or bare; validated by a `.git` entry of either kind or a bare `HEAD`, then cloned *from*) if set, else the repo URL (`TEMPLATE_REPO` env > manifest `template.repo`). A repo URL on the old Bitbucket SSH host (`git@bitbucket.org:` / `ssh://git@bitbucket.org/`) is mapped to `ssh.bitbucket.org` before it is cloned, with an INFO line — Bitbucket no longer serves SSH on `bitbucket.org`, and a manifest written before the move still names it. Check 8.5 maps a recorded or passed `FRONTEND_REPO` the same way. A mirror cloned from the old spelling counts as the same origin and is re-pointed, not re-cloned. Phase 8's advance writes the mapped URL back (`scripts/lib/bitbucket-url.sh`).
- If a clone already exists at `$CACHE` (spared by the fresh-mode sweep, or from a continue run) **and** it mirrors the same origin, `git remote update --prune` refreshes it in place. Otherwise — no clone, wrong origin, or a corrupt/unreachable one — `git clone --mirror origin → $CACHE` from scratch (removing any partial clone first). `--mirror` (not `--bare`) gives the `+refs/*:refs/*` refspec that makes the refresh path exact. Then `git worktree prune` on the clone.

**Trade-off (deliberate).** The clone lives inside the component, not a shared home-directory cache — per-component isolation, no cross-component races, no home-directory side effects. It is kept across runs and refreshed with a fetch, so a repeated fresh run or an interrupted-and-resumed migration doesn't re-pay the full clone. Only the first run on a component (or an origin change / corrupt clone) pays a full clone; a local `--template-path` origin makes even that fast (hardlinks on the same filesystem) and is the recommended origin for template authors iterating locally.

**8. Local template intent signal** (only when `TEMPLATE_PATH` is set). Emits `TEMPLATE_LOCAL_BRANCH=<branch>` — the branch the local clone actually has checked out — so Phase 2's default chain can prefer it over the manifest branch (a template author co-developing on a feature branch means "migrate against what I have here"). A detached-HEAD clone emits no line; a remote-URL origin has no working checkout, so nothing is emitted. Separately, a **dirty local template working tree** produces a non-fatal `WARNING`: uncommitted content never reaches the mirror clone and is therefore invisible to the whole migration. Non-fatal by design — deliberate co-dev workflows edit here constantly; the warning informs, it does not block.

**8.5. Frontend source — the second upgrade source.** `web/` is not part of the template merge: it is a **template-shaped source with its own repo, its own SHAs and its own run**, so pre-flight reads what the component records about it and emits it as facts for the later phases that decide anything (Phase 2's frontend target chain, the frontend materialize, Phase 8's consent step). **Silence is a feature**: a component with no `frontend:` block and no `web/package.json` emits nothing, records nothing, and costs a backend-only migration zero new lines and zero new prompts.

- **The recorded block**, when `.kairos/manifest.yaml` has one: `FRONTEND_REPO`, `FRONTEND_SHA`, `FRONTEND_BRANCH`, `FRONTEND_TEMPLATE`, `FRONTEND_MODULE_PATH`, `FRONTEND_MOUNT`. Two of those are not verbatim copies. `FRONTEND_TEMPLATE` is the module **key**, not a path — it selects the entry in the source repo's `.kairos-updates/config.yaml` that supplies the subtree, the per-module upgrade-file directory and the bellwethers, so nothing in the skill assumes `react`; `FRONTEND_MODULE_PATH` is the manifest's own `path`, the fallback subtree when that config is absent. And `mount:` is **optional with a `web/` default, materialized here, once** — so no later reader has to remember the default, and none can default it differently.
- **`FRONTEND_BOOTSTRAP`** — no block, but `web/package.json` exists: a pre-existing component whose frontend baseline was never recorded. The check is the file, not the directory: both template refs ship a `web/` shell (`Dockerfile`, `configs/`, `entrypoint/`) with no `package.json`, and that shell is not a frontend — it emits nothing. Emitted as `FRONTEND_BOOTSTRAP=web/` plus an INFO line, and it is a **candidate, not a decision**: nothing here starts a run or scores anything, Phase 2's frontend bootstrap does that (score, show the top matches, one confirmation covering module *and* commit) and only after the consent step has asked.
- **`--frontend-path` normalization** (only when `FRONTEND_PATH` is set) — the analog of check 7/8's `--template-path`, with one difference that matters: **the module subtree is not a git repo of its own.** The history, `.kairos-updates/config.yaml` and the per-module upgrade-files all live at the monorepo root, so a path *inside* the checkout (e.g. `…/template/react`) is accepted and **normalized to the enclosing git toplevel** (`git rev-parse --show-toplevel`, compared against `pwd -P` so a symlinked ancestor cannot make the root look like a subtree), with an INFO line saying so. A path that is **not inside a git work tree is refused** — including a bare or mirror clone, which has no work tree to normalize. When the given path *was* a subtree and it does not match the module the manifest selects, a `WARNING` says so and names both: the run uses the **manifest's** module either way (`frontend.template` is what selects it), so the author who pointed at a different module hears about it instead of migrating against something they weren't looking at. Then `FRONTEND_PATH=<toplevel>` is emitted, plus `FRONTEND_LOCAL_BRANCH=<branch>` when that checkout is on one — the strongest statement of "migrate against what I have here", and rule 2 of Phase 2's frontend target chain. A **dirty** local frontend working tree produces the same non-fatal `WARNING` check 8 gives for the template: uncommitted content never reaches the mirror clone and is invisible to the whole migration.

**8.6. The frontend mirror** (only under `RUN_SOURCE=frontend`). A frontend run's own `--mirror` clone of the frontend source, at `.kairos/migration/state/frontend`, emitted and recorded as `FRONTEND_CACHE`.

- **Why here and not at materialize.** Three consumers need the mirror *before* Phase 2.5 runs, and none of them can build it: Phase 2's frontend arm validates `BASE` and the resolved target against it, the frontend bootstrap scores the mount against candidate commits in it, and Phase 3's classification walks the module's upgrade-file history in it. All three previously read `CACHE` — the **template** mirror — in which a frontend SHA resolves to nothing and the module's upgrade-file directory does not exist, so a frontend run refused two perfectly good SHAs (or reported an empty range) and the message blamed the SHAs.
- **Origin**, in order: `FRONTEND_PATH` (the normalized local checkout) → the manifest's `frontend.repo` → the `FRONTEND_REPO` env, which exists for the **bootstrap** case (a legacy component has no block, so no recorded URL); when the env fills that gap, the value is emitted and recorded so Phase 2's bootstrap writer has it. No origin at all on a frontend run is a hard failure naming all three.
- **Reuse rule identical to check 7's**: an existing mirror of the **same** origin is refreshed with `remote update --prune`; a different origin, a corrupt mirror or a failed refresh is a clean re-clone. Then `git worktree prune`.
- **A template run pays none of this and emits nothing** — the frontend source is not its source, and cloning a monorepo it will never read is pure cost.

**9. Record run context.** Upserts into `$RUN/context.env` (via `record-context.sh`, after the fresh-mode sweep so the sweep can never delete what this run just recorded): `CACHE` and `SKILL_DIR` always, `RUN_SOURCE` when the invocation declared one (this script is the first to know the run's source — checks 0b and 3 already acted on it — so it is the recorder; Phase 2's own write of the same key then re-states it idempotently, and a template run that passed nothing records nothing, exactly as before), `TEMPLATE_PATH` when set, `TEMPLATE_LOCAL_BRANCH` when check 8 found one. It also records the frontend facts, on the same rule and for the same reason — `FRONTEND_PATH` and `FRONTEND_LOCAL_BRANCH` when a local checkout was given, the six block keys when a `frontend:` block exists, `FRONTEND_BOOTSTRAP` when one does not but `web/` is there, `FRONTEND_REPO` when the env filled the bootstrap gap, and `FRONTEND_CACHE` on a frontend run (check 8.6). Only when there **is** a frontend source: absence of these keys stays the record of "this component has none", which is what lets the consent step recognise the silent case. `SKILL_DIR` is recorded here — absolute, derived from this script's own location — because it is the value *every* later phase code block needs to locate the scripts, and it is the one the orchestrator can least afford to be re-deriving from memory after a compaction; this is also the run's first write to the anchor, which is what lets every block after Phase 1's first call open by reading it (SKILL.md → Run-context anchor). The script that learns a value records it — Phase 3.5's `wrong-target-check.sh` reads `TEMPLATE_PATH` from `context.env`, never from conversation memory, so the tripwire stays armed across compaction and resume. A fresh run without `--template-path` sweeps the old state dir and therefore leaves no stale `TEMPLATE_PATH` line.

**10. Sweep the tracked `PLAN.md`.** In fresh mode, once every check above has passed (this is the ONE tracked-file write pre-flight makes), removes `.kairos/migration/PLAN.md` if a committed one survives from a completed or crashed prior run. Deferred out of check 6's fresh-mode sweep — which only touches the gitignored `state/` scratch — because `PLAN.md` is a **tracked, committed** file: deleting it before an earlier check (the clone in check 7, the `context.env` write in check 9) could still fail would leave a tracked deletion sitting in the working tree, which check 1's clean-tree gate would then refuse on the very next fresh re-run ("working tree is dirty") — wedging a clean re-run the user never dirtied. Nothing between check 6 and here reads `PLAN.md`, so running this once pre-flight is certain to succeed is equivalent to sweeping it earlier, minus that failure mode. Same fresh-mode-only, no-in-progress-block guard as check 6: a live or continuing run's `PLAN.md` is never touched — continue depends on it.

## Deliberately NOT here

**Baseline/target SHA validation.** `BASE` and `TARGET` are only resolved in Phase 2 (manifest read + `rev-parse` against the cloned cache), so validating them here would check variables that don't exist yet. Phase 2 runs `git cat-file -e <sha>^{commit}` on both immediately after resolving.

## Failure mode

Any failure exits cleanly — no branch created, no manifest mutations. Anything the script does write is confined to the gitignored `.kairos/migration/` scratch (the stale-state sweep and the template clone); a failed clone leaves at most an empty state dir the next fresh run sweeps. The user fixes the issue and re-runs. The orchestrator should NOT try to auto-recover pre-flight failures — they all require user action (commit your work, check out a branch, configure the template repo, install a missing tool, resume or abort the run already in progress).
