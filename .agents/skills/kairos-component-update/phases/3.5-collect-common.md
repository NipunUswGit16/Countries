## Phase 3.5: Collect common-library upgrade-files

PHASE_KEY: 9059z5gm
(Proof-of-load: this phase's scripts — `extract-template-gomod.sh` first, then `collect-common.sh` — refuse to run without `PHASE_KEY=9059z5gm` in their environment. The key is stated only in this file — never copy it into SKILL.md or another phase.)

**Frontend run (`RUN_SOURCE=frontend`): this phase is IDLE, and idle is a PASS.** Common is a Go-library dependency of the component, not of a frontend module: a frontend run changes no `go.mod`, so there is nothing for this phase to collect, resolve or trip over. The layers that sit still are the whole phase — common-library collection, the `go.mod` replace-directive (co-development) scan, and the wrong-target tripwire — plus the Kairos CLI version probe (`phases/1-preflight.md`, check 0b, three phases earlier), whose actual *use* is Phase 2.5's `component create` materialization: a frontend run needs neither, because its mount is materialized from git trees and the replacement map, never by `component create`. **Record every one of them as *not applicable*, never as *incomplete*:** the completeness gates ask whether each layer was answered, and "no `go.mod` in scope" is an answer. Reporting it as a gap invites someone to satisfy it by running the template's common collection into a frontend baseline. Read the arm off the anchor rather than remembering it:

```bash

COMMON_MODULES=$(sed -n 's/^COMMON_MODULES=//p' "$RUN/context.env")
```

`frontend` → skip everything below, relay the not-applicable rows, and go to Phase 4. Otherwise take the `COMMON_MODULES` branch below. The silenced-test scan is **not** part of this idle set — it runs on a frontend run too (its JS/TS needles already exist), and it lives in Phase 8's finalize, not here.

The `kairos-component-common` libraries are a **dependency, not a merge** — they contribute upgrade-files only, riding the same planner/executor pipeline as template upgrade-files. The `go.mod` version bump itself is carried by the existing template `go.mod` structural merge (Phase 5); there is no separate bump step and no common-only migration mode.

**Branch on `COMMON_MODULES` in `$RUN/context.env`, never on `COMMON_CACHE`** — clone-common wrote both in Phase 1, and they answer different questions, so you never need the Phase 1 conversation to decide:

- `COMMON_MODULES=none` → **skip this phase entirely.** No artifacts, no prompts, nothing to relay.
- `COMMON_MODULES=present` and `COMMON_CACHE` set → the full path below.
- `COMMON_MODULES=present` and `COMMON_CACHE` empty or absent → the clone failed, but **run collection anyway** — a degraded run, not a stopped one:
  1. The script tolerates an unset cache and records one `skip-no-cache` row per module in `common-resolution.tsv` — the visible record a failed clone should leave. Relay that tally and continue.
  2. `skip-no-cache` is a settled outcome, not an `unresolvable`, so the batched unresolvable question below does not fire for those modules.
  3. **But do not read that as "`common-unresolvable.txt` stays empty".** The two co-development arms never consult `COMMON_CACHE` at all: a local-path `replace` (template-side *or* the component's own) collects against the *local* clone, or lands `unresolvable` when that clone cannot bound the range; a `REF_OVERRIDES` row lands `unresolvable` because there is no mirror to resolve its ref in. Both funnel into `common-unresolvable.txt`, so a co-developed component reaches the batched question on this arm too — ask it exactly as on the full path. (How each end of a co-dev range is sourced — BASE from the surviving `require` pin, the local path supplying only the HEAD end — is `reference/upgrade-files.md` → *Co-development resolution*.)

**Go toolchain floor.** Compare the target's `go` directive (`awk '$1 == "go" { print $2; exit }' "$RUN/template-go.mod"`) with `go env GOVERSION`. Target ≤ installed → nothing to do. Target higher and `go env GOTOOLCHAIN` is `local` → stop before Phase 5 and tell the user to install that Go version or allow toolchain downloads: every post-merge build and test would fail on the toolchain, not on the merge. Target higher otherwise → tell the user the first post-merge build downloads that toolchain.

**`COMMON_REPO_PATH` and `COMMON_CACHE` come off the anchor, never from the Phase 1 conversation** — `clone-common.sh` recorded both there itself, one phase and possibly one compaction ago. This is the phase where a lost value is most expensive and least visible:

- **A lost `COMMON_CACHE`** — `collect-common.sh` reads an unset cache as "the clone failed" and writes one `skip-no-cache` row per module, silently dropping the common-library upgrade-files of every module resolved **through the mirror**, behind a tally that looks exactly like a real degraded run. On a co-developed component the loss is only *partial* — a local-path `replace` still collects against its local clone, a ref override still resolves or lands `unresolvable` — which makes it harder to spot in the tally, not easier.
- **A lost `COMMON_REPO_PATH`** is worse — no module matches the prefix, so the module set itself comes out empty and even the skip rows disappear.

Neither is recoverable later: Phase 6 freezes `PLAN.md` and nothing re-derives the applicable set — which is why both are read off the anchor, not from memory.

**Never extract it with a bare redirect.** A redirect creates the file before `git show` runs, so a bad ref leaves a zero-byte `template-go.mod` — which both readers below score as "no requires, no replaces", and the wrong-target tripwire, whose whole job is to catch a wrong TARGET, then reports clear. The script verifies the extraction is a go.mod before installing it, and a refusal leaves any previous good extraction untouched.

Detect co-development mechanically — do not rely on noticing it:

```bash
RUN=.kairos/migration/state; ctx() { sed -n "s/^$1=//p" "$RUN/context.env" | tail -1 | grep . || echo "FAIL: $1 missing from $RUN/context.env" >&2; }
SKILL_DIR=$(ctx SKILL_DIR); COMMON_REPO_PATH=$(ctx COMMON_REPO_PATH)
# Capture the EXIT STATUS, not just the output: the script's contract is exit 0 =
# parsed (with or without matches), exit 2 = could not parse, with empty stdout in
# both the no-matches and the failure case — so output alone cannot tell them
# apart (see codev-check.sh's header for why discarding the status is unsafe).
COMMON_REPO_PATH=$COMMON_REPO_PATH "$SKILL_DIR/scripts/codev-check.sh" "$RUN/template-go.mod"; CODEV_RC=$?
echo "CODEV_RC=$CODEV_RC"
```

Branch on the result — the exit status first, then the output:

- **Exit 2 — could not parse; never "no replaces".** The `FAIL:` line on stderr names the cause (missing/unreadable `template-go.mod`, `go` not on PATH, a malformed go.mod). Re-run `extract-template-gomod.sh` for an extraction problem, or fix the named tool; if it still exits 2, stop and surface — proceeding on the plain path here silently disarms the co-dev detection *and* the wrong-target tripwire's premise.

- **Replaces present + a local `--template-path`** → co-dev mode, automatically. Resolve the replaces against the **real template directory**, not the state dir: read the path off the anchor (`TEMPLATE_PATH=$(sed -n 's/^TEMPLATE_PATH=//p' "$RUN/context.env")` — pre-flight recorded it; empty means no local template, which is the next arm), then pass **only** `TEMPLATE_GOMOD_DIR="$TEMPLATE_PATH"` in the collect call below. `TEMPLATE_GOMOD` stays `$RUN/template-go.mod` in every branch — version truth comes from the `go.mod` at TARGET, never from the working template checkout; co-dev changes only where the relative-replace resolution looks, never where versions come from.
- **Replaces present + no local template path** → ask ONE batched question **up front**, before per-module resolution is reported: for the co-developed modules, does the user (a) point at a local common checkout, (b) name a common ref already pushed and resolvable in the mirror cache, or (c) skip. Route the answer mechanically — a named ref becomes a `REF_OVERRIDES` row (below); a local checkout becomes a `TEMPLATE_GOMOD_DIR` that resolves the relative replace; a skip needs no input at all — provide nothing, let those modules land as `unresolvable`, and disposition them as skip in the batched funnel below. **Ask it in the user's terms** (SKILL.md → Speaking to the user): "co-developed modules" and "the mirror cache" are internal — say that the component looks like it's being built together with the shared library, and offer the three ways to get that library's update steps. E.g. *"This component's `go.mod` points the shared library at a local folder, so it looks like you're developing the two together. To include the library's update steps I can: use a copy of it on your machine (tell me the folder), use a version or branch you've already pushed (tell me its name), or skip the library's changes for now. Which?"*
- **No replaces** → plain path, resolution behavior unchanged.

```bash
SKILL_DIR=$(ctx SKILL_DIR); COMMON_REPO_PATH=$(ctx COMMON_REPO_PATH)

  "$SKILL_DIR/scripts/collect-common.sh"
```

`TEMPLATE_GOMOD` is always the plain default here, a literal value rather than a live-shell `${TEMPLATE_GOMOD:-…}` read — this is a fresh tool call, so a shell variable set while deciding the co-dev branch above is already gone, and defaulting through it would silently make the working template checkout the version source instead of TARGET's own `go.mod` (see the co-dev bullet above for why that distinction matters). `TEMPLATE_GOMOD_DIR` is this phase's own co-dev branch decision, minutes old — set it explicitly, in this same call, to whichever directory the branch above resolved; leave it empty for the plain no-replaces path.

**A `TEMPLATE_GOMOD` that is absent, a directory, unreadable, or not parseable as a go.mod is a hard error (exit 1) raised before any module is resolved** — every module's TARGET comes from that file, so reading it as "pins nothing" would mark the whole module set `skip-absent-target` and exit 0 with a plausible tally. Shape is judged by `go mod edit -json` itself rather than a stricter grep of our own, and its message is relayed — a UTF-8 BOM, for instance, is diagnosed with go's own precise "unexpected input character" rather than a generic "carries no module line" (the script's header has the full rationale). If it fires, re-run `extract-template-gomod.sh` and re-run this phase; never proceed on the empty resolution.

The refusal writes **no new rows this run** — but it does not clear a *previous* run's `common-resolution.tsv`, so a re-used `$RUN` still holds the last successful run's rows on disk. Don't read them as this run's answer; a hard error means the module set was never resolved, whatever the file says.

The script (mechanics in its header and `reference/upgrade-files.md`, including the full meaning of each decision code) writes into `$RUN`:

- `common-resolution.tsv` — per module: BASE, TARGET, decision (`collect` / `skip-downgrade` / `skip-absent-target` / `skip-no-cache` / `unresolvable`) — see `reference/upgrade-files.md` for what each code means and why.
- `common-unresolvable.txt` — modules whose range can't resolve; the only code that feeds the batched question below.
- `common-upgrades-added.txt` / `.tsv` — collected upgrade-files with source/module provenance, bodies snapshotted into the shared `$RUN/upgrades/`.
- `common-upgrades-modified.txt` — common upgrade-files that existed before a module's BASE and were amended in range (mirrors the template's `upgrades-modified.txt`), also snapshotted into `$RUN/upgrades/`.
- `common-supersede-edges.tsv` — `module <TAB> superseder-stem <TAB> superseded-stem <TAB> kind` — the `supersedes:` edges parsed from the collected bodies (see `reference/upgrade-files.md` → Superseding prior guidance). This collector's OWN file (never shared), written unconditionally so `supersede-check.sh` can tell present-and-empty from a missing collector run.
- `common-legacy-upgrade-commits.txt` — ceiling-gated legacy `UPGRADE.md` commits.
- `snapshot-refusals.tsv` — shared with Phase 3 (`slug <TAB> source <TAB> reason`). This phase appends its own rows (source id `<module>:.kairos-updates/…`) and replaces only those on a re-run, so Phase 3's rows survive. Two reasons land here with different remedies, same split as Phase 3: a body `git show` could not read fails the same way on a re-run — re-fetch the common mirror, or have the planner disposition that slug explicitly; a row whose reason names `mv failed` was read but could not be written into `$RUN/upgrades` — check that the directory is writable and has space, then re-run collection, which does clear it. A zero-byte snapshot is *not* a refusal: a common upgrade-file committed empty is collected and served as an empty body (`reference/upgrade-files.md`).

**Surface unresolvable modules before the expensive phases.** If `common-unresolvable.txt` is non-empty, present all rows as ONE batched question — per module: skip it, provide a ref/tag, or abort. A "provide a ref" answer is **mechanically actionable**: write the module→ref lines to a TSV and re-run collection with it — no hand-collection.

**Phrase it for a component owner, not for yourself** (SKILL.md → Speaking to the user). "Unresolvable module" and "provide a ref/tag" mean nothing to them; name the *shared library* and what each choice costs. The three options translate to: **skip** = leave that library's changes out of this update (they can do them later); **provide a ref/tag** = point me at a folder on your machine, or a version/branch name, where that version of the library lives; **abort** = stop the whole update. E.g. *"Your component uses the shared `toolkit` library. I couldn't tell which of its update steps apply, because the version you're moving from (`v1.0.44`) isn't in the copy I have. You can: skip toolkit for now, point me at a folder or a version/branch where `v1.0.44` exists, or stop the update. I'd suggest skipping unless you're actively changing toolkit yourself."*

**Wrong-target tripwire — mandatory before Phase 4 on every run that reaches this point; a `STOP` outcome (exit 2 or 3 below) blocks the run until the user resolves it.** **Run the block below regardless of `COMMON_CACHE`'s state** — it reads `TEMPLATE_PATH` from `$RUN/context.env` itself (never from conversation memory), and a run with no local template exits 0. Why it is always safe to run here: the arms that never reach this point — the frontend skip and `COMMON_MODULES=none` — exited this phase earlier by design, so "mandatory" binds the `present` continuation, the only path still here; and it is defense in depth behind the Phase 2 default chain — the `COMMON_MODULES=none` skip arm at the top of this phase already exited before any of this ran, so this block is never dispatched without `extract-template-gomod.sh` having already written `$RUN/template-go.mod` a few tool calls earlier (the extraction runs for both branches of `present`, `skip-no-cache` included):

```bash
RUN=.kairos/migration/state; ctx() { sed -n "s/^$1=//p" "$RUN/context.env" | tail -1 | grep . || echo "FAIL: $1 missing from $RUN/context.env" >&2; }
SKILL_DIR=$(ctx SKILL_DIR)
RUN=$RUN "$SKILL_DIR/scripts/wrong-target-check.sh"
```

Branch on the exit code (stdout is empty; the verdict lines are on stderr):

- **0** — not applicable (no local template recorded) or clear. Proceed.
- **2** — **STOP and ask**: the working tree co-develops common but TARGET contains no replaces — the `STOP:` block lists the working-tree replaces. Ask whether the target is right before the hours-long phases run.
- **3** — **STOP and ask**: could not determine — a recorded `TEMPLATE_PATH` whose `go.mod` is gone, an unreadable `go.mod` on either side, or missing run context. A lost `TEMPLATE_PATH` must surface as a question, never as silence — do not treat this as clear.

Read the decision tally from stderr — don't `cat` the TSVs. The planner (Phase 6) sees these common upgrade-files alongside the template ones (grouped by provenance, apply order its decision); finalize (Phase 8) re-verifies every applied upgrade-file regardless of source. Record in `.kairos/migration-log.md` which ref or SHA each collected common module came from (the `collect` rows' detail/target in `common-resolution.tsv`) so unreleased-source provenance is auditable.
