**Two arms, one per source — `RUN_SOURCE` on the anchor decides which, and each block asserts its own.** A template run materializes through the Kairos CLI (below); a frontend run materializes the module subtree itself (last section). Everything after this phase is identical for both.

### Template run (`RUN_SOURCE=template`)

The merge does not read the template's own blobs. It reads two trees built by the
same command that created the component — so substitution can never drift from it
(`reference/materialization.md`). **Never substitute placeholders yourself.**

```bash
RUN=.kairos/migration/state; ctx() { sed -n "s/^$1=//p" "$RUN/context.env" | tail -1 | grep . || echo "FAIL: $1 missing from $RUN/context.env" >&2; }
SKILL_DIR=$(ctx SKILL_DIR); CACHE=$(ctx CACHE); BASE=$(ctx BASE); TARGET=$(ctx TARGET)
RUN_SOURCE=$(ctx RUN_SOURCE)
[ "$RUN_SOURCE" = template ] || { echo "FAIL: RUN_SOURCE is '$RUN_SOURCE', not template — a frontend run materializes with the block at the end of this file (the CLI cannot produce a frontend side at all)"; exit 1; }
export CACHE BASE TARGET RUN
MAT_OUT=$(PHASE_KEY=n41g1bxq "$SKILL_DIR/scripts/materialize.sh"); MAT_RC=$?
[ "$MAT_RC" -eq 0 ] || { echo "FAIL: materialize.sh exited $MAT_RC — stop the phase"; exit 1; }
SYNTH=$(printf '%s\n' "$MAT_OUT" | sed -n 's/^SYNTH=//p')
[ -n "$SYNTH" ] || { echo "FAIL: materialize.sh printed no SYNTH= line"; exit 1; }
export SYNTH
```

**Check the exit status before extracting `SYNTH`** — that is what the two guards above are. Piping the script straight into `sed` takes `sed`'s status, which is 0 whether the script succeeded or failed; a failed materialization then yields an empty `SYNTH`, and the run continues into Phase 3 classifying against nothing. The script's own contract makes the check sufficient: it exits non-zero with a `FAIL:` line on every failure path (a CLI create that failed twice, a missing mirror, a tree the CLI did not produce) and prints `SYNTH=` only on success — including the stamped-reuse path. Relay its message verbatim and stop; do not re-run it hoping for a different answer.

Both trees land in a throwaway repo at `$RUN/synthetic` (tags `kairos-base` /
`kairos-target`), already substituted and already LF — so from Phase 3 on a
synthetic path *is* a component path. Re-running is cheap (inputs are stamped), so
Continue mode doesn't re-pay it.

Two artifacts to relay:

- **`$RUN/materialization.txt`** — whether a corrective module-path substitution
  fired (the component's root `go.mod` is the authority when it disagrees with the
  CLI's `bitbucket.org/ifs-pd/<name>` convention). Relay it; **nothing in it stops
  the migration.** The only hard stop in this phase is the script's own non-zero
  exit, whose message you relay verbatim.
- **`$RUN/surviving-tokens.tsv`** — placeholder-shaped tokens the CLI didn't
  substitute. **Template feedback, not errors**: don't stop, carry them to Phase 8.

### Frontend run (`RUN_SOURCE=frontend`)

Same two-tree contract, different builder: `scripts/materialize-frontend.sh`
extracts the module subtree at each SHA, maps it onto the mount, and applies the
**create-time replacement map** — because `component create` copies that subtree
verbatim and then substitutes across the whole component including the mount, so a
raw subtree would conflict against the component's `web/` on every substituted
file. **No Kairos CLI is involved and no CLI version is probed on this arm** (the
CLI can only clone the frontend at branch HEAD, which is neither BASE nor TARGET);
the CLI-parity claim is carried instead by the contract test in
`tests/materialize-frontend.test.sh`, and the map still lives in exactly one place
— **never substitute placeholders yourself here either.**

```bash
RUN=.kairos/migration/state; ctx() { sed -n "s/^$1=//p" "$RUN/context.env" | tail -1 | grep . || echo "FAIL: $1 missing from $RUN/context.env" >&2; }
SKILL_DIR=$(ctx SKILL_DIR); BASE=$(ctx BASE); TARGET=$(ctx TARGET); RUN_SOURCE=$(ctx RUN_SOURCE)
# Bare reads: every FRONTEND_* key is legitimately absent (SKILL.md → Run-context
# anchor), and empty IS an answer — no local checkout was given, no mount was
# recorded because the mount is the default. The script fills what the anchor does
# not carry from the manifest's frontend block and fails loudly if neither has it.
# FRONTEND_TEMPLATE is the module KEY, and it is passed as MODULE because the script
# resolves the subtree from the source's own .kairos-updates/config.yaml at TARGET with
# it, falling back to FRONTEND_MODULE_PATH: passing the key is what lets an upstream
# module RELOCATION be followed instead of failing at extraction against a stale path.
FRONTEND_TEMPLATE=$(sed -n 's/^FRONTEND_TEMPLATE=//p' "$RUN/context.env")
FRONTEND_MODULE_PATH=$(sed -n 's/^FRONTEND_MODULE_PATH=//p' "$RUN/context.env")
FRONTEND_MOUNT=$(sed -n 's/^FRONTEND_MOUNT=//p' "$RUN/context.env")
FRONTEND_PATH=$(sed -n 's/^FRONTEND_PATH=//p' "$RUN/context.env")
FRONTEND_REPO=$(sed -n 's/^FRONTEND_REPO=//p' "$RUN/context.env")
# The mirror pre-flight check 8.6 established (and check 6's sweep spares). Passed
# explicitly rather than left to the script's default, so the run that validated its
# SHAs against a mirror materializes from that same mirror.
FRONTEND_CACHE=$(sed -n 's/^FRONTEND_CACHE=//p' "$RUN/context.env")
[ "$RUN_SOURCE" = frontend ] || { echo "FAIL: RUN_SOURCE is '$RUN_SOURCE', not frontend — use the template arm above"; exit 1; }
export RUN BASE TARGET
MAT_OUT=$(PHASE_KEY=n41g1bxq RUN="$RUN" BASE="$BASE" TARGET="$TARGET" \
  MODULE="$FRONTEND_TEMPLATE" MODULE_PATH="$FRONTEND_MODULE_PATH" MOUNT="$FRONTEND_MOUNT" \
  FRONTEND_CACHE="$FRONTEND_CACHE" \
  FRONTEND_PATH="$FRONTEND_PATH" FRONTEND_REPO="$FRONTEND_REPO" \
  "$SKILL_DIR/scripts/materialize-frontend.sh"); MAT_RC=$?
[ "$MAT_RC" -eq 0 ] || { echo "FAIL: materialize-frontend.sh exited $MAT_RC — stop the phase"; exit 1; }
SYNTH=$(printf '%s\n' "$MAT_OUT" | sed -n 's/^SYNTH=//p')
[ -n "$SYNTH" ] || { echo "FAIL: materialize-frontend.sh printed no SYNTH= line"; exit 1; }
export SYNTH
```

The exit-status guards are load-bearing for the same reason they are on the template
arm — check the status **before** extracting `SYNTH`, relay the script's `FAIL:`
message verbatim, and stop. Its hard stops are: a SHA that does not resolve in the
frontend mirror, no module subtree resolvable at all (neither the source's config nor
the manifest names one), a module path absent at one side, an empty extracted subtree,
a subtree carrying `.kairos-updates`, a failed replacement map, and the same install /
clear failures the template arm has.

**Relay its `WARN:` about a relocated module.** When the source's `config.yaml` at
TARGET puts the module somewhere other than the manifest's `frontend.path`, the script
uses the **source's** value and says so: the run is correct, but the component's
recorded `path` is stale and the user is the only one who can fix it — surface the line
and suggest updating `.kairos/manifest.yaml`. The subtree is resolved **per side**, so a
module that moved *inside* `BASE..TARGET` materializes from its own path at each end
(the second `WARN:`) instead of refusing — both sides still land on the same mount, so
the classification shows content changes plus adds/deletes for files the two subtrees
do not share, never a rename of the mount. Relay that one too.

The script records the **resolved** `FRONTEND_MODULE_PATH`, `FRONTEND_CACHE` and
`FRONTEND_MOUNT` on the anchor alongside `SYNTH`/`BASE`/`TARGET` — that is what makes
Phase 8's parity basis the subtree this run actually merged rather than the manifest's
possibly-stale one.

What lands is the same shape, narrowed to one subtree: `$RUN/synthetic` with tags
`kairos-base` / `kairos-target`, holding **the mount and nothing else** — every
other component path is legitimately absent from both sides, so the classifier
produces no row for it and the template run's baseline is untouched. Relay
`$RUN/materialization.txt` (module, mount, both SHAs, `cli: none`) and carry
`$RUN/surviving-tokens.tsv` to Phase 8 as **frontend-template** feedback; neither
stops the run.
