An empty `TEST_CMD`/`BUILD_CMD`/`REGEN_CMD` is a legitimate record (the script writes the literal placeholder), but a `TEST_CMD` with no `EXTRACTOR` is refused — that pair is already a `gate-internal` FAIL downstream, so it stops here instead.

`run-check-modules.sh` wraps `run-check.sh`: a non-`go` command — and a Go component whose only module is the root — delegates verbatim, artifacts byte-identical. A `go` command with sibling `go.mod` modules is swept across all of them (rationale: `reference/gates.md`). **The baseline goes through the same wrapper as the gates**, so a root-only baseline is never compared against a swept gate run.

`run-check.sh` writes raw combined output gzip-compressed to `$RUN/test-baseline.txt.gz`, and pipes it through the `EXTRACTOR` in the same run to produce `$RUN/test-baseline.failures.txt` — a sorted set of failing test IDs, the one plain-text artifact every later comparison uses. On a non-zero exit it also writes bounded plain-text `$RUN/test-baseline.excerpt.txt` for triage; decompress the `.gz` only when you need the full log for post-mortem inspection.

Use the sharpest extractor the toolchain offers: `go test -json` filtered for `"Action":"fail"`, `pytest --tb=no -q` tail parsing, jest/vitest reporters — or as a floor, `grep -E '^(FAIL|--- FAIL|✗)' | sort -u`. Pass it as `EXTRACTOR` so the postmerge gate and planner apply the identical one — the Phase 5 and Phase 8 gates read it back themselves, and the planner copies it into PLAN.md's `## Test Baseline` section, which is where the executor's copy comes from (it never reads `test-command.txt` directly). Downstream, "regression" always means: a test ID in the new failure set but absent from `test-baseline.failures.txt` — compare failure sets, never raw output.

**Zero-evidence guard.** Require evidence of work or discard the candidate for the next in the preference order (full rationale — vacuous green, `make vet` example, do-nothing patterns — in `reference/gates.md`):

- **Test**: `$RUN/test-baseline.status` reads `OK` (empty failure set, suite ran green) or `FAIL` with a non-empty `test-baseline.failures.txt`. `EXTRACTOR_MISMATCH` discards the candidate — every later gate would read that silence as green. An `OK` status over output matching the do-nothing patterns below is still vacuous; discard it too. There is a **fourth** status, and it is not a pass: `SKIP`, written when the test sweep found **no module carrying tests at all**, so not one module ran a check (`run-check-modules.sh` refuses to call that `OK` — it would be the vacuous green the gates exist to reject). Treat it as **no baseline evidence**: surface it to the user in those words, never read it as green, and expect the tests row downstream to be as weak as it is on a component with no test command at all.
- **Build**: applies wherever `BUILD_CMD` is actually run — its output must not match a do-nothing pattern (`No directories changed`, `no packages to build`, `nothing to be done`, zero targets). **On a template run this phase only discovers and records `BUILD_CMD` (convention order below, under *Also discover a build/typecheck command*); nothing here executes it.** Its first real run is Phase 5's postmerge gate — that is where a vacuous candidate (a bare `make vet` slipped past the convention order) actually surfaces, so treat a do-nothing result there as cause to swap the recorded command before Phase 6 freezes the plan, not as a Phase 4.5 refusal. **On a frontend run** this phase DOES run one — the component-root build baseline below (`build-baseline-root`) — and the guard applies to that output directly, at capture time, exactly like the Test bullet above.
- **Census status, read separately from the test status** (it disqualifies no candidate — it records how much evidence you got): `$RUN/test-baseline.census.status` can also read `ABSENT` — no module produced a census — which matches **neither** arm of the empty-baseline-population refusal above (that keys on `MISMATCH` or `FAILED`, and on `OK` over an empty population file). `ABSENT` is not a refused recipe; it means the census was simply not captured. Record that honestly: the census row reads `INCOMPLETE` downstream (`reference/gates.md` → *The census row*), a coverage gap to relay into the migration log, never a clean row.

The positional `$RUN/test-command.txt` contract — which line carries which command, and how rejections are appended — lives in `reference/gates.md` (its one home; Phases 5, 7, and 8 read the same contract). It is `write-test-commands.sh`'s documentation, not yours to re-enact: pass the four values and let the script place them.

**Also discover a build/typecheck command — line 3, always, even when tests exist.** Try in this order so the zero-evidence guard has a defined next candidate: (1) `make build` if the target exists by the toolkit check above (the Kairos toolkit has no `build` target, so a Kairos component lands on (2)), (2) the language's whole-tree check (`go build ./...`, `tsc --noEmit`, `cargo check`, `python -m compileall`), (3) any other target that compiles everything. **Also discover a regeneration command — line 4.** The producer-idempotence gate (Phases 5 and 8) needs the tree's generator the same way the build gate needs its compiler: run it, and tracked state must not move. Discover it convention-ordered, exactly one, or nothing: `make generate` if the target exists by the toolkit check above (toolkit resolves and `make -n generate` succeeds), else the language's canonical codegen entry point if declared, else the literal `no regen command`. **Which kairos-gen `make generate` runs.** Check `grep -q 'kairos-component-common/cmd/kairos-gen' go.mod`, then the toolkit version (`go list -m -f '{{.Version}}' bitbucket.org/ifs-pd/kairos-component-common/toolkit`):

## Frontend run (`RUN_SOURCE=frontend`)

The baseline means the same thing here — what passed *before* the merge — but its cwd, its commands and the evidence it can produce all move to the mount.

**Discovery is not yours: pass `MOUNT` and let the script read the mount's `package.json`.** The one command a reader would reach for first is the one that must never be recorded — the frontend template's default `test` script is watch-mode `vitest`, which never exits, so a gate that ran it would *hang* the migration instead of failing it. `write-test-commands.sh` picks the non-interactive CI entry (`test:ci`, else a test-named script whose body is `vitest run`-shaped — a `--ci` flag on a `lint` or `e2e` script is not a test suite — else the runner invoked directly on evidence it is installed), records the mount's `build` as line 3 with `typecheck` **joined** to it (a type check is not a test run and never stands in for one), and leaves the rejected watch-mode candidate as a `# rejected:` line below line 4. It also looks for a `generate` script in the mount's `package.json` and records that as line 4 when present, exactly like the template arm's regen discovery below (else the literal `no regen command`). The component root's `make test` is never even looked at: it does not see the mount, so it can never be the frontend suite.

```bash
RUN=.kairos/migration/state; ctx() { sed -n "s/^$1=//p" "$RUN/context.env" | tail -1 | grep . || echo "FAIL: $1 missing from $RUN/context.env" >&2; }
SKILL_DIR=$(ctx SKILL_DIR); RUN_SOURCE=$(ctx RUN_SOURCE)
# Bare read: every FRONTEND_* key is legitimately absent (SKILL.md → Run-context
# anchor). On a frontend run it is not — an empty MOUNT here means the run lost the
# mount, so stop rather than discovering against the component root.
MOUNT=$(sed -n 's/^FRONTEND_MOUNT=//p' "$RUN/context.env")
: "${MOUNT:?FAIL: FRONTEND_MOUNT missing from the run-context anchor — stop; pre-flight check 8.5 records it (it defaults to web/), and discovering against the component root would record the WRONG suite}"
[ "$RUN_SOURCE" = frontend ] \
  || { echo "FAIL: this is the frontend section but RUN_SOURCE=$RUN_SOURCE — take the template path instead" >&2; exit 1; }
# $RUN is relative, and the calls below run with cwd at the mount: a relative path
# would resolve to <mount>/.kairos/migration/state and write the baseline inside web/.
RUN_ABS=$(cd "$RUN" && pwd -P)
RUN=$RUN MOUNT="$MOUNT" PHASE_KEY=u7qk3mfp CENSUS="" "$SKILL_DIR/scripts/write-test-commands.sh"
# The baseline runs the MOUNT suite, through the commands just recorded — read back
# from the file rather than retyped, so the gate and the baseline can never diverge.
TEST_CMD=$(sed -n 1p "$RUN/test-command.txt"); EXTRACTOR=$(sed -n 2p "$RUN/test-command.txt")
( cd "$MOUNT" && CHECK=test CMD="$TEST_CMD" EXTRACTOR="$EXTRACTOR" \
    OUT="$RUN_ABS/test-baseline" PHASE_KEY=u7qk3mfp "$SKILL_DIR/scripts/run-check-modules.sh" )
```

A non-`go` command delegates through the wrapper verbatim, so the mount suite is captured exactly as a single-module run — and **the gates use the same cwd**: every later frontend gate (`gate.sh` at the Phase 5, midplan and final labels) is invoked with cwd at the mount, unchanged, so what the baseline measured is what they compare against. `gate.sh` needs no frontend flag; the cwd *is* the parameter.

**A loud failure here is the correct outcome, not something to work around.** If the mount declares no non-interactive entry at all — no `test:ci`, nothing `vitest run`-shaped, no vitest to fall back on — the script writes nothing and exits 2. Do not record `no tests detected` to get past it and do not fall back to the root suite: relay the message (the remedy is a `test:ci` script in the mount, and upstream in the frontend template) and stop.

**The census is Go-specific, so on a frontend run it is best-effort.** The `-json` recipe above is a Go recipe; there is no equivalent obligation here. Pass `CENSUS=""` as the block does — `$RUN/census-command.txt` then carries the literal `no census extractor`, the census row reads `INCOMPLETE` downstream, and that is the honest record. **A missing test population on a frontend run is an incomplete-coverage row to relay, never a block**: it never moves the aggregate, and it is not a reason to refuse the baseline. If the mount's runner does offer a machine-readable per-test form, recording it is welcome — under exactly the same two census-specific checks as the Go arm (non-empty population, consistent status), and the empty-baseline-population refusal applies unchanged.

**Also baseline the component-root build, once.** Phase 8's frontend final gate adds the component-root **build** after the mount checks pass (`phases/8-finalize.md` step 1) — the layer that catches a `web/` merge breaking the Go entrypoint or its embed. That build is not line 3: line 3 is the *mount's* build and the two run in different cwds, so nothing else records what the root build did *before* the merge, and a pre-existing root breakage would surface at finalize looking exactly like one this run caused. Run it here, at the component root, discovered by the same convention order the template arm uses for line 3 (`make build` if the target exists, else `go build ./...`, else the language's whole-tree check), and keep the status as this run's datum — a plain artifact, not a positional line, so it cannot shift anything the gates read:

```bash
RUN=.kairos/migration/state; ctx() { sed -n "s/^$1=//p" "$RUN/context.env" | tail -1 | grep . || echo "FAIL: $1 missing from $RUN/context.env" >&2; }
SKILL_DIR=$(ctx SKILL_DIR)
# No PHASE_KEY: that guard is the `test-baseline` stem's alone (run-check-modules.sh).
# Multi-module by construction, which is what makes it cover web/entrypoint.
CHECK=build CMD="<the component-root build command>" OUT="$RUN/build-baseline-root" EXTRACTOR= \
  "$SKILL_DIR/scripts/run-check-modules.sh"
```

Relay its status. A root build that was **already** failing before the merge is a fact to state now and to carry into the finalize entry — not a reason to stop the frontend run, and not something the final extra should be allowed to blame on `web/`.

**Layers with nothing to do under the mount don't all land the same status — `gate.sh` is unchanged, and it reports each one with the vocabulary it already has.** A frontend mount usually has no YAML for the YAML gate to parse and no Helm chart at all: those layers correctly PASS on "nothing found" — a YAML-less, chart-less mount isn't a partial check, it's a check with nothing to report, so say so in the relay (*not applicable — no YAML / no chart under the mount*) rather than leaning on the word PASS unexplained. Producer-idempotence is different: a mount with no generator lands `INCOMPLETE` ("no build or regeneration command recorded"), and that one IS a real coverage gap worth carrying into the migration log as incomplete semantic coverage — reserve that phrasing for it, not for the layers that PASS. **The silenced-test scan still runs and still counts** — its needles cover the skip/pending constructs across Go, JS/TS, Java and Python (`t.Skip*`, `.skip`, `.todo`, `xit`/`xdescribe`, `@Disabled`/`@Ignore`, `pytest.mark.skip[if]`), so a frontend run can silence a test exactly as a template run can. A bespoke skip helper or a test silenced by commenting out its assertions is an accepted false negative (`scripts/silenced-tests.sh`'s header) — no needle grammar catches those.
