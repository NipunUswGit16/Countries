# Integration API

The component's REST surface for **service-to-service communication** — the interface other backend services and systems use to integrate with this component.

## Overview

The integration API is built on the Go Fiber framework. Where the [client API](client-api.md) is a BFF (backend-for-frontend) that talks only to the component's own frontend, the integration API is the **system-facing** surface: it is how *other services* call into this component. Its handlers follow the same thin pattern as the client API — parse input, delegate to a service via the `ServicesFactory`, format the response — and services may publish domain events or send commands via the `OutboundMessenger`.

Out of the box it ships with one built-in capability, **bulk data loading**, exposed at `POST /api/core/v1/load`. External systems (legacy databases, Spark jobs, third-party feeds) send batches of entities and the endpoint upserts them into PostgreSQL in parallel. Components add their own service-to-service endpoints alongside it via `internal/integration-api/routes.go`.

The integration api machinery (including the loader endpoint) lives in `kairos-component-common/api/integration` and a new instance can be created invoking the `New` function. This function will setup the api and the loader endpoint.

Everything loader-specific is code-generated by `kairos-gen` from your domain entities — you rarely hand-write a loader.

## Load Request Flow

The flow below is for the built-in `load` endpoint; custom endpoints follow the standard client-API handler → service flow instead.

```
HTTP Request (POST /api/core/v1/load)
    ↓
Middleware Stack (authentication, tenant resolution, etc.)
    ↓
Loader Handler (parses the multi-entity request)
    ↓
Loader Registry (looks up a loader per entity _type)
    ↓
Parallel Worker Pool (each worker holds a dedicated connection)
    ↓
Per-entity: Parse → Validate → Prepare → UPSERT (ETag-guarded)
    ↓
Response (200 OK with per-entity results)
```

## The Entity Load Endpoint

The one endpoint provided out of the box by the common library:

```
POST /api/core/v1/load
```

The API router is mounted at `/api`; the entity load route lives under `/core/v1`. There is no per-entity-type listing endpoint — the registry is internal.

### Request Body

Entities of different types may be mixed in one request; each carries its own `_type` discriminator.

```json
{
  "entities": [
    { "_type": "customer", "data": { "id": "550e8400-...", "name": "John Doe" } },
    { "_type": "product",  "data": { "id": "660e8400-...", "name": "Wireless Mouse" } }
  ],
  "force": false
}
```

| Field                | Type   | Required | Description                                                                                             |
| -------------------- | ------ | -------- | ------------------------------------------------------------------------------------------------------- |
| `entities`           | array  | yes      | Entities to load. Types may be mixed; each carries its own `_type`.                                     |
| `entities[]._type`   | string | yes      | Entity-type discriminator. Must match a loader registered on the server, else `UNKNOWN_ENTITY_TYPE`.  |
| `entities[].data`    | object | yes      | The raw entity payload. Its shape is defined by the loader's domain type. **Must include the `id`.**  |
| `force`              | bool   | no       | Defaults to `false` (guarded upsert — respects the stored ETag). Set `true` to overwrite unconditionally. |

**Batch size and worker count are server-controlled** (via config, see below), not per-request.

### Response

Even when some entities fail, the HTTP status is `200`; per-entity outcomes live in `results`. Only infrastructure-level failures (unreachable schema/table, DB client unavailable, request exceeds the size limit) return `4xx`/`5xx`.

```json
{
  "success": true,
  "message": "Load completed successfully",
  "data": {
    "id": "ci1a2b3c4d5e6f7g8h9",
    "summary": { "total": 3, "succeeded": 2, "skipped": 1 },
    "results": [
      { "index": 0, "status": "created" },
      { "index": 1, "status": "updated" },
      { "index": 2, "status": "skipped", "reason": "etag" }
    ]
  }
}
```

- `message` is `"Load completed successfully"`, or `"Load completed with partial success"` when `summary.failed > 0`.
- `summary` counts are omitted when zero (`succeeded`, `failed`, `skipped`).
- `results[].index` is authoritative and maps back to the entity's position in the request; result order is not relied upon.

### Statuses, Reasons, and Error Codes

| Status    | Meaning                                        |
| --------- | ---------------------------------------------- |
| `created` | New record inserted.                           |
| `updated` | Existing record updated (UPSERT matched).      |
| `skipped` | Intentionally not applied (see `reason`).      |
| `failed`  | Processing failed (see `error`).               |

Skip reasons (`results[].reason`): `duplicated` (duplicate id within the request) or `etag` (incoming ETag not newer than the stored one).

Failure codes (`results[].error.code`): `UNKNOWN_ENTITY_TYPE`, `PARSE_ERROR`, `VALIDATION_ERROR`, `PREPARE_ERROR`, `BUILD_ARGS_ERROR`, `DATABASE_ERROR`, `SESSION_ERROR`, `TIMEOUT`, `INTERNAL_ERROR`.

For the complete request/response contract, see the loader README in `kairos-component-common/api/integration/loader/README.md`.

## Entity Loaders

A loader tells the engine how to handle one entity type. The interface (from `kairos-component-common/api/integration/loader/types`) is:

```go
type EntityLoader interface {
    EntityType() string                                              // "customer"
    TableName() string                                               // "customers"
    ParseEntity(data []byte) (entities.Entity, error)                // JSON → typed entity
    PrepareForUpsert(ctx, entity) (entities.Entity, error)           // validate id, set ETag/timestamps
    GetBatchUpsertQueryParts() QueryParts                            // structured SQL for the batch upsert
    BuildUpsertArgs(entity) ([]any, error)                           // SQL arguments per row
}
```

Most entities need none of this by hand. The library ships `StandardEntityLoader[T, TId]`, which handles the common two-column `(id UUID, data JSONB)` case for any domain type `T` that embeds `entities.EntityBase[TId]`. The entity type name is derived from the struct name (lowercased), so a `Customer` struct becomes `_type: "customer"`.

### Adding a Loader

Do **not** hand-edit `internal/integration-api/loaders/generated/register.go` — it is code-generated (`// Code generated by kairos-gen. DO NOT EDIT.`). To add a loader, invoke the **`kairos-create-loader`** skill; it creates the loader and wires its registration into the generated registry. Registration ultimately funnels through:

```go
// internal/integration-api/loaders.go
func RegisterLoaders(apiInstance integrationapi.LoaderRegistryProvider) {
    registry := apiInstance.LoaderRegistry()
    generated.RegisterLoaders(registry)
}
```

### Optional Interfaces

A loader's entity type may additionally implement any of these (all from the `types` package):

- **`Validator`** — `Validate(ctx) error` for field-level validation (required fields, formats, business rules).
- **`LoaderValidator`** — `LoaderValidate(ctx) error` for loader-only validation; takes precedence over `Validator`.
- **`IdStringer`** — `EntityIdString(entity) string` to override id-to-key mapping when the id's default string form does not match the `id::text` produced by PostgreSQL (used for skip reconciliation).

## Data Storage

Entities are stored in a standard two-column table:

```sql
CREATE TABLE customers (
    id    UUID PRIMARY KEY,   -- taken from the entity payload (NOT generated by Kairos)
    data  JSONB NOT NULL      -- the full entity, including base fields
);
```

`PrepareForUpsert` requires the `id` to be present in the request payload; it does **not** generate one. It sets the ETag if absent, sets `created_at` on first insert, and always updates `updated_at`. The stored `data` JSONB contains the entity's fields plus the base fields (`id`, `etag`, `created_at`, `updated_at`).

Query stored data with standard PostgreSQL JSONB operators:

```sql
SELECT * FROM customers WHERE data->>'name' = 'John Doe';
```

## Request Context

Integration-API handlers use a `request.Context` type alias, mirroring the client API and event handler:

```go
// internal/integration-api/request/context.go
type Context = apicontext.Context[ServicesFactory, config.AppConfig]
```

Inside a handler, `request.Context` exposes the same accessors as the client API — `DatabaseSession()`, `Logger()`, `Config()`, `ServicesFactory()`, `Sender()`, `Tracer()`, `TenantId()`, and `CorrelationId()` (see [client-api.md](client-api.md)). If the component only does data loading, the `ServicesFactory` stays empty and the built-in `load` endpoint is the whole surface; to add your own endpoints, see [Adding a Handler](#adding-a-handler) below.

## Adding a Handler

Beyond loading data, the integration API is a general service-to-service REST surface, and adding an endpoint is **almost identical to the client API** — same handler signature, same `request.Context`, same `ServicesFactory` pattern, same response helpers. The only difference is *where* it lives: `internal/integration-api/routes.go` and `internal/integration-api/request/` instead of `internal/api/`.

Handlers implement the standard signature:

```go
func GetInventory(ctx request.Context) error
```

Register them in `routes.go`, wrapping each with `commonapi.Handler` so the framework injects the `request.Context`:

```go
// internal/integration-api/routes.go
func InitRoutes(router fiber.Router) {
    v1Group := router.Group("/v1")
    v1Group.Get("/inventory/:sku", commonapi.Handler(handlers.GetInventory))
}
```

A handler parses input, gets a tenant-scoped session, calls a service through the `ServicesFactory`, and returns via the `commonapi` helpers:

```go
func GetInventory(ctx request.Context) error {
    db, err := ctx.DatabaseSession()
    if err != nil {
        return commonapi.ErrorResponse(ctx, fiber.StatusInternalServerError, "Failed to get database session", err)
    }
    defer db.Close()

    service := ctx.ServicesFactory().CreateInventoryService(ctx, db)

    item, err := service.Get(ctx.Context(), ctx.Params("sku"))
    if err != nil {
        return commonapi.ErrorResponse(ctx, fiber.StatusInternalServerError, "Failed to load inventory", err)
    }

    return commonapi.SuccessResponse(ctx, item, "OK")
}
```

Because the pattern is shared with the client API, the authoritative references for handler shapes are in [client-api.md](client-api.md): the [synchronous vs asynchronous (command) shapes](client-api.md#endpoint-shapes), `commonapi.RequestBody[T]` for parse-and-validate, the response helpers, and the middleware stack (auth, tenant resolution, transaction management) all apply here unchanged. The `ServicesFactory` here lives in `internal/integration-api/request/services_factory.go`; use the `kairos-create-api-endpoint` skill (and `kairos-create-service` for the service behind it) to scaffold both correctly.

## Configuration

Loader behaviour is tuned through environment variables (defaults come from `kairos-component-common/api/integration/config`):

| Variable                             | Default | Description                                                                 |
| ------------------------------------ | ------- | --------------------------------------------------------------------------- |
| `LOAD_BATCH_SIZE`               | 100     | Entities per INSERT batch sent to a worker.                                 |
| `LOAD_MAX_PARALLEL_WORKERS`     | 5       | Parallel workers processing batches.                                        |
| `LOAD_MAX_ENTITIES_PER_REQUEST` | 1000    | Reject the whole request with `400` if exceeded (`0` disables the limit).   |
| `LOAD_HANDLER_RESERVED_CONN_COUNT` | -1   | Pooled connections reserved for non-loader handlers. `-1` derives `poolSize/2`; `0` disables the cap. |

The connection cap keeps parallel loader workers from starving the rest of the component of database connections.

## Key Concepts

### Idempotency & the ETag Guard
The load is an UPSERT and is safe to retry. With `force=false` (default), an incoming entity only overwrites the stored row when its ETag is newer; otherwise it is `skipped` with reason `etag`. Set `force=true` for a deliberate full re-seed that overwrites regardless.

### Tenant Isolation
All writes are scoped to the tenant resolved from the request by middleware — each worker opens a connection into the correct per-tenant schema.

### Deduplication
Duplicate ids *within a single request* are detected by parsed id (catching differing representations, e.g. UUID letter-case). One winner is applied; the losers are `skipped` with reason `duplicated`.

### No Foreign-Key Constraints
JSONB storage means there are no database-level FK constraints. If entities reference each other (e.g. a `user` referencing an `institute`), the **caller** is responsible for migrating referenced entities first. Use `Validator`/`LoaderValidator` for field-level checks; there is no cross-entity existence check.

### Fail-Fast on Infrastructure
Before processing, the handler verifies the target tables exist in the tenant schema. A missing schema/table fails fast as a `5xx` rather than surfacing as misleading per-entity `DATABASE_ERROR` results under a `200`.
